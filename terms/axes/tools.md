# 维度 5 · 工具与扩展

> 核心问题：**它能让模型做什么？怎么接新工具？**

---

## 这个维度分两层

**第一层**：内置能力（自带哪些工具）
**第二层**：扩展机制（能不能接更多，接得上吗）

这两层必须分开写。厂商宣传常混为一谈。

---

## 要回答的四个子问题

### 5.1 内置工具能力

| 类别 | 例子 |
|---|---|
| 文件 | 读写、搜索、重命名、批量操作 |
| 执行 | 跑命令、跑测试、跑构建 |
| 浏览 | 内置浏览器、网页抓取 |
| 检索 | 代码搜索、文档检索、库 API 查询 |
| 版本控制 | git 操作、diff、commit |
| 外部服务 | 数据库、邮件、第三方 API |

**判定**：列出实际有的，不列"计划支持"。

### 5.2 MCP 支持

这是 2026 年的关键分水岭。

| 问题 | 说明 |
|---|---|
| 客户端支持 MCP | 能不能连 MCP server |
| 支持哪些传输 | stdio / SSE / Streamable HTTP |
| 有没有内置 MCP | 开箱即用的 server |
| MCP 是核心还是边缘 | 影响稳定性预期 |

**常见误解**：
```
连接器可用不等于有模型订阅权限；
不能用 provider 支持列表推断免费额度。
```

### 5.3 扩展机制

| 机制 | 说明 |
|---|---|
| 插件系统 | 有正式插件市场/manifest |
| 自定义指令 | 能否写可复用的 prompt |
| Hooks | 能否在特定时机插入脚本 |
| 子代理 | 能否派发独立子任务 |

### 5.4 稳定性信号

**从 changelog 反推的能力边界比文档更真实**：

```
9 月 28 日：超时控制、MCP 浏览器启动失败反馈、
调试凭据脱敏和 Gemini 推理参数修正。
```

四个修复里两个是权限/可靠性相关——**这说明这条工具链的实际成熟度低于版本号给人的印象。**

---

## 常见错误

| 错误写法 | 问题 |
|---|---|
| `工具丰富` | 太空泛，无法判断 |
| `支持 MCP` | 没说哪些传输、有没有内置 |
| `可扩展性强` | 主观判断，无证据 |
| 列官方 roadmap | roadmap 不是现有能力 |

---

## 合格的写法

```markdown
tools: >-
  内置文件读写、命令执行、浏览器、代码检索与 git 操作。
  支持 MCP（stdio / Streamable HTTP），
  有若干内置 server；也支持自定义指令与 Hooks。
  **插件市场是否存在本次未核验，记为未知。**
```

拆解：
- 内置能力列清了
- MCP 说清了传输方式和内置情况
- 不知道的部分标出来

---

## MCP 分区专项

MCP server 本身就是"工具"，所以这个维度要换成：

| 字段 | 说明 |
|---|---|
| `tools_count` | 提供几个 tool |
| `tools_capability` | 每个 tool 做什么 |
| `output_format` | 结构化还是自由文本 |

**输出质量比数量重要**。10 个返回自由文本的 tool，不如 3 个返回结构化结果的 tool。

判定见 [mcp/taxonomy/](../tracks/mcp/taxonomy/)。
