# 维度 8 · 适合什么任务

> 核心问题：**它最擅长干什么？什么情况下别用它？**

---

## 这是唯一需要主观判断的维度

前 7 个维度都是可核验的事实。这个维度是编辑判断。

**所以它必须标注为判断，不能伪装成事实。**

---

## 正确的写法：任务具体到场景

### 不合格

```
适合日常开发
```
问题："日常开发"包含从改一行 typo 到重构整个模块，跨度太大，等于没信息。

### 合格

```
适合：
已有仓库开发、改错、重构、测试与工程交付。
```

**判定标准**：读完这一句，你能判断"我要干的活属于这一类吗"。

---

## 三种写法

### 写法 A · 正向定位

```
适合：已有仓库开发、改错、重构、测试与工程交付。
```

### 写法 B · 边界排除（更有价值）

```
注意：
只为轻量问答购买最高档；
把「最高模型」当成任何任务的默认选择。
```

**排除法往往比定位更有用**，因为人已经知道自己要干什么了。

### 写法 C · 条件化

```
适合：中文资料整理、日常办公、文档产出与轻量开发。
不适合：需要 IDE 级代码掌控、严格 Diff 和大型仓库工程闭环的任务。
```

---

## 「注意」字段是本站最高价值的原创内容

看几个例子：

| 对象 | 注意（原文） |
|---|---|
| Codex | 只为轻量问答购买最高档；把「最高模型」当成任何任务的默认选择。 |
| WorkBuddy | 把活动赠送积分当成永久套餐额度；将在线入口等同无条件后台运行。 |
| Manus | 误以为 My Computer 在本机关机后仍运行；未经审核打开自动发布。 |
| Qoder | 把 Quest 当作长期入口；将开发者云服务视为桌面订阅自动附送的后台电脑。 |
| Kimi | 把 K2.6 文本输出当成原生文件；把 Work 的本地任务误当作 Claw 云任务。 |
| Claude | 把 Opus 运行成本下降理解成订阅降价；把所有新功能写成全套餐立即可用。 |
| Muse | 在未确认地区可用性和权限时迁移全部个人数据；把即将上线的眼镜当成现有能力。 |

**这七条的共同特征**：每条都是**一个具体的、真实存在的用户误解**。

这些是官网不会写、论坛说不全、只有真的用过才会知道的东西。

---

## 怎么找到「头号误解」

按这个顺序找：

1. **产品改名或产品线合并时** → 用户会分不清哪个是哪个
2. **有多个入口时** → 用户会把 A 入口的能力当成 B 入口的
3. **有限额或活动时** → 用户会把活动当永久
4. **有新功能预告时** → 用户会把预告当现有
5. **价格结构复杂时** → 用户会误解额度关系

## pitfalls 字段要求

```yaml
pitfalls:
  - 把「最高档模型」当成任何任务的默认选择
  - 以为索引是实时的，大仓库首次打开需等
```

**约束**：
- 1-3 条，每条 ≤60 字
- 每条是一个**误解**，不是提醒
- 不合格：`注意性能问题`（太空泛）
- 合格：`以为索引是实时的，大仓库首次打开需等`（具体可验证）
- 不合格：`注意安全风险`（太空泛）
- 合格：`默认请求全盘访问权限，如需收紧要手动配置`（具体）

## 与实测的关系

**这个维度最需要实测支撑。**

如果做过实测，可以写得更准：

```
适合：单文件修改、快速问答、单点调试。
不适合：跨 10+ 文件的重构——本轮实测中，
三家工具在跨模块重构时都出现了约束丢失。
```

**"不适合"的部分要给出证据**（本轮实测的具体表现），不能只是推测。

---

## 常见错误

| 错误写法 | 问题 |
|---|---|
| `适合各种场景` | 等于什么都没说 |
| `功能强大，适用面广` | 营销话术 |
| `不适合新手` | 价值判断，不是能力边界 |
| 只写适合不写注意 | 用户看不到风险 |

## 合格范例

```markdown
fit: >-
  已有仓库开发、改错、重构、测试与工程交付。
  纯问答场景性价比低。
```

正文配合：

```markdown
## 适合

已有仓库开发、改错、重构、测试与工程交付。

## 注意

只为轻量问答购买最高档；
把「最高档模型」当成任何任务的默认选择。
```
