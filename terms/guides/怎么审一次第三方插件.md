# 怎么审一次第三方插件（How to Audit a Third-Party Plugin）

**这份指南解决什么**：接一个第三方 MCP server 或插件之前，审四件事：它要什么权限、代码从哪来、数据往哪去、出事谁负责。

**怎么做**：
1. 列权限清单：它能读哪些目录、能不能发网络请求、能不能执行命令。超出用途的权限要么砍掉，要么不接。
2. 看代码来源与维护状态：仓库归属、近期提交、issue 里有没有安全回应，比 star 数更能说明问题。
3. 数据流向问三句：日志记不记提示内容、要不要回传厂商、是否用于训练。答不清楚就按「会外传」处理。
4. 先在隔离环境跑：独立账号、最小权限、只喂测试数据，把工具调用日志留在能查到的地方。
5. 按注入风险测一轮：在工具描述或返回内容里放一句「忽略之前的指令」，看它是否被执行——间接提示注入常出现在工具返回里，而不是用户输入里。
6. 定退出方案：换掉它要改哪几处、历史数据怎么清、谁批准。没有退出方案的接入，等于把依赖写进架构。
7. 举个例子（虚构流程）：输入是一个声称「只读项目 README」的文件系统 server → 处理是在沙箱里只给它一个目录并禁止网络 → 结果判断是看它是否只访问该目录、调用日志是否只落本地 → 若它请求了目录外路径，下一步是收回接入并按 OWASP 的 LLM 风险项记一条，而不是仅降权限继续用。

**出处**：风险类别取自 OWASP 的 LLM / GenAI 清单；本站档案页记录了两类 server 的权限边界与安全警告。例子里的 server 行为是虚构流程。
