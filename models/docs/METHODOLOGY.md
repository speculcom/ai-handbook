# 方法论

> 本站所有数据都从公开来源读取，逐条标注出处。**我们不跑 benchmark，不给主观优劣排名。**
> 这份文档说明：我们收什么、怎么收、哪些话是我们能说的、哪些话不能说。

## 一句话

**这个站只回答一个问题：这个基础模型，我该下载哪个量化版、为什么。**

不做「哪个模型更强」的横评——那需要实测，我们不做。
只做「同一个模型的多个量化版之间怎么选」——这部分靠公开事实就能说清。

## 数据来源

| 来源 | 取什么 | 性质 |
|---|---|---|
| `huggingface.co` 模型页 | 许可、架构、上下文长度、下载量、更新时间 | 事实 |
| HF API `/api/models/{id}` | `cardData.license`、`gguf.architecture`、`gguf.context_length` | 事实 |
| HF API `/api/models/{id}/tree/main?recursive=1` | 每个 `.gguf` 文件的真实体积（字节） | 事实 |
| llama.cpp 公开量化命名标准 | 从文件名推断量化类型与每权重比特数 | 推导 |

**我们不下载任何权重文件**，只读元数据。页面上出现的每个数字都能点回发布页核对。

## 选型方法：首批系列是怎么定下来的

不是拍脑袋定的，是从数据反推的：

**第一步 · 找真实热度**
拉 HF 上 `filter=gguf&sort=downloads` 的量化仓榜单（按真实下载次数），
再排除「微调衍生仓」（`abliterated` / `uncensored` / `heretic` / `Distilled` / `Merged` / `Derestricted` 等）——
因为那些是别人拿别人家权重再训再发的二次发布，不是「基础模型的量化版」。

**第二步 · 反推基础模型**
把剩下的仓按模型标识归组，得到「本地部署圈真正在下载的量化版」TOP N。

**第三步 · 厂商定向核对**
对每个厂商查当前最新代的基础模型，再看它有没有 GGUF 量化覆盖。

**第四步 · 四维打分**

| 维度 | 含义 | 权重 |
|---|---|---|
| D1 量化热度 | 头部量化仓下载量（log） | 40 |
| D2 量化广度 | 有多少家量化者跟进了（竞争充分度） | 25 |
| D3 规模可及性 | 是否存在单卡可跑的密集档 | 20 |
| D4 基础新鲜度 | 官方仓距上次更新的天数 | 15 |

**落选示例**（有量化但太冷，不上站）：

| 系列 | GGUF 量化总下载 | 落选原因 |
|---|---|---|
| Mistral-Small-4-119B | 3.5 万 | 量化热度比入选者低两个数量级 |
| Llama-4-Scout-17B | 3.8 万 | 同上，且是 2025-04 的老代 |
| MiniMax-M3 | 1.7 万 | 同上 |
| Intern-S2-397B | 0.8 万 | 同上，397B 规模本地跑不动 |

**最终收录（7 个系列 / 11 个规格）**

按 GGUF 量化实际下载量排序，这是本站全部收录：

| 系列 | 规格数 | 许可 | 量化仓 | 入选理由 |
|---|---|---|---|---|
| **Qwen 3.8**（千问 3.8） | 2 | apache-2.0 / other | 17 | 27B 断层第一（2123 万下载），本地部署圈事实标准 |
| **Gemma 4** | 3 | apache-2.0 | 26 | 三种规格都有量化：MoE 26B-A4B / 密集 31B / 小尺寸 E4B |
| **GLM 5** | 2 | other / mit | 17 | 智谱最新代；Flash 版是 MIT，本地部署法律上最干净 |
| **DeepSeek V4** | 1 | mit | 7 | MIT 许可，antirez（llama.cpp 作者）亲自维护量化 |
| **gpt-oss** | 1 | apache-2.0 | 4 | 单卡甜点（20B / 激活约 3.6B），许可最干净 |
| **Kimi K3** | 1 | other | 10 | 月之暗面最新代，41 家量化仓但整体热度中等 |
| **MiniCPM 5** | 1 | apache-2.0 | 9 | 国产端侧代表（2B），官方自己出 GGUF |

> **`gpt-oss-20b` 是 2025-08 发布，严格说不算「最新代」。**
> 保留它的理由：唯一同时具备成熟量化生态 + apache-2.0 + 单卡可跑的对象，
> 对比价值高于「只要最新」。

**用户明确要求的策略（2026-09-30）**：
> 「这一轮采的这些模型都选那些最新的模型，老的不要采」

因此以下都**不收录**：`Qwen3-30B-A3B` / `Qwen3-8B` / `Qwen3-32B` / `Qwen2.5-*` / `Llama-3*` / `Llama-4-*` /
`Gemma-3*` / `Mistral-7B-*` / `GLM-4*` / `DeepSeek-V3*`。老代一律不进站，
只在用户问「上一代还能用吗」时才提一句。

## 我们能说什么、不能说什么

这是本站最重要的一节。

### ✅ 能说（A 级 · 客观事实）

直接从 API 读到的字段，页面上标注为「实测字段」：

- 文件体积（字节，来自 HF tree API）
- 上下文长度（`gguf.context_length`）
- 架构（`gguf.architecture`）
- 许可（`cardData.license`）
- 下载量、点赞数、更新时间
- 某个量化者提供了哪些档位
- 是否带 importance matrix

### ✅ 能说（B 级 · 参数推导）

由 A 按明确规则算出，页面上标注为「推导」：

- **每权重比特数**：从文件名量化标签按 llama.cpp 公开命名标准推算
  （例：`Q4_K_M` → 4.83 bpw，`IQ4_XS` → 4.25 bpw）
- **档位归属**（极限压缩 / 长上下文优先 / 平衡档 / 保守档 / 近似无损）：由 bpw 落档
- **显存需求区间**：由文件体积 + KV cache 估算（标注为估算）

**推导规则完整写在 `SCHEMA.md`，任何人可以复算。**

### ❌ 不能说（C 级 · 主观优劣）

这些我们**不写**，或者写了必须明确标为「我们的口径」：

- 「这个量化比那个质量高」
- 「这档速度快」
- 「这个模型推理能力强」
- 「建议日常用这个」

**理由**：这些都需要实测才能断言，本站不跑 benchmark，所以不装作知道。

我们会写的例子：

> 「动态量化（`UD-` 前缀）在同档位下体积略大、速度略慢，换来的是质量通常更好。
> 是否值得取决于你的瓶颈是显存还是速度——**这是我们的口径，不是实测结论**。」

## 许可处理

- 许可字段一律从发布页 `cardData.license` 读取，**不解读、不总结、不改写**
- `other` / `cc-by-*` / `gpl` / `openrail` 等非宽松许可，页面显著位置显示：
  **「以发布页原文为准」** 并给出原文链接
- 官方 GGUF 与第三方量化**严格分开**，官方仓排在最前
- 继承关系如实标注：「继承基础模型许可；量化产物本身由量化者发布」
- 本站**不托管任何权重文件**，只提供发布页链接

## 已知局限

诚实地说明我们做不到什么：

1. **不跑实测** → 质量优劣、速度数据一律不给
2. **bfw 是按命名推算** → 实际每权重比特数因模型而异（同为 `Q4_K_M`，不同模型的真实 bpw 略有差异）
3. **下载量会变** → 页面标注采集时间，数据快照而非实时
4. **可能漏仓** → HF 搜索接口有索引延迟，冷门量化仓可能搜不到；限流时可能跳过部分仓库（跳过记录在 `collect-log.json`）
5. **不做横向能力对比** → 那是 benchmark 站的事

## 更新流程

```
1. config.js        改系列名单（新增/下架）
2. collect-models.mjs  重跑采集（约 6~9 分钟，注意 hf-mirror 限流）
3. audit-licenses.mjs   跑审计（不合规则中止建站）
4. build.mjs            生成站点
5. 部署 + 验证线上
```

数据快照的采集时间会印在每个系列页底部，方便判断新鲜度。

## 参数量怎么来的（为什么不用 API 声明值）

HF 公开 API 的 `safetensors.total` 对 MoE 模型**只给总参**，而用户判断「要多少显存能跑」
关心的是**每个 token 实际激活的参数量**。`config.num_parameters` 在这批新模型上普遍缺失。
靠 `config` 的结构参数（`hidden_size` / `intermediate_size` / `num_experts_per_tok`）
反推激活量，需要下载 `model.safetensors.index.json`（Kimi-K3 有 49 万个张量条目），
成本高且容易出错——实测这些字段在新模型上大多取不到。

**所以本站的做法是：**

1. 参数量用**实测反推**：`文件字节数 × 8 ÷ 该档 bpw`。
   这个方法在密集模型上与官方声明交叉验证通过 ——
   Qwen3.8-27B 反推 28.9B vs 声明 27B、gemma-4-31B 31.6B vs 31B、gpt-oss-20b 19.2B vs 20B。
2. MoE 模型**只标总参并注明「激活数未公开」**，不呈现任何猜测的激活值。
3. 用户要判断显存，看系列页 B 区**按实测体积倒推的选档表**——
   那个表直接给出「你的显存能下哪个文件」，不需要用户自己换算参数量。

> 这是本站的立场：宁可标注「未公开」，也不给一个看起来精确但来源不明的数字。
