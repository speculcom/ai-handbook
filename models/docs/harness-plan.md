# Harness 站规划（P3）

> 定位：**中间层**。用户用 IDE/CLI（产品层），Agent 调 MCP（组件层），
> 而 Harness 是把「工具 · 记忆 · 恢复 · 审批 · 可观测」编排起来的那一层。

## 一句话

**Harness 决定 Agent 能不能在真实工作里连续跑几个小时不出错。**
它不酷，但你项目跑到一半崩了、忘了、或者误删了，都是 harness 的问题。

## 与其他站的关系

```
产品层   IDE（Cursor / Windsurf / …）· CLI（Claude Code / Codex / …）
   ↓ 用户在界面里直接用，关心「好不好用」
组件层   MCP（给 Agent 调用的工具）—— 不直接给人用
   ↓
模型层   models.specul.com（本地部署量化模型）
   
横跨中间   Harness  ← 本站
   = 工具接入 / 记忆与状态 / 恢复与检查点 / 审批与权限 / 可观测性 / 部署形态 / 许可 / 语言支持
```

**为什么 Harness 必须单独立站**：
- IDE/CLI 是「形态」，用户第一句话是「我在哪用」
- MCP 是「工具粒度」，用户在选「Agent 能调用什么」
- Harness 是「编排逻辑」，用户在选「长时间任务靠不靠得住」

三者回答的是不同的问题，混在一张表里没法比。

## 8 个对比维度

| 维度 | 要回答的问题 | 数据来源 |
|---|---|---|
| **工具接入** | 怎么注册工具？支持 MCP 吗？支持多少并发？ | 官方文档 |
| **记忆与状态** | 多轮之间怎么记？状态存哪？有 checkpoint 吗？ | 官方文档 + SDK 源码 |
| **恢复与检查点** | 崩了能续上吗？能回滚到某一步吗？ | 官方文档 |
| **审批与权限** | 危险操作能拦吗？谁能批？ | 官方文档 |
| **可观测性** | 有 trace 吗？能导出吗？接什么平台？ | 官方文档 |
| **部署形态** | 库 / CLI / 服务 / 云？ | 官方文档 |
| **许可** | Apache-2.0 / MIT / 自定义商业条款？ | 仓库 LICENSE |
| **语言支持** | Python / TS / Go / Rust？ | 仓库语言构成 |

## 三级可信度（与 models 站一致）

| 级别 | 含义 | 例子 |
|---|---|---|
| ✅ 实测字段 | 从仓库/文档直接读到 | 许可、语言、星标数、最后提交日 |
| ✅ 推导 | 由实测字段按规则算出 | 「成熟度」= 更新频率 + 版本稳定性 |
| ❌ 我们的口径 | 主观判断 | 「适合长任务」「学习曲线陡」 |

## 核心区块设计

每个对象页：

1. **A · 它是什么** —— 官方定位 + 归属方 + 一句话
2. **B · 该不该自己搭** —— 决策区：什么场景该自己写 harness，什么场景直接用现成的
3. **C · 8 维度对比表** —— 横向可比
4. **D · 各维度详解** —— 每维度展开，含「不同实现怎么取舍」
5. **E · 代码形态** —— 最小可运行示例（从官方文档摘录，标注出处）
6. **F · 更新记录** —— 版本历史 + 维护活跃度

首页：
- 层次地图（四层关系图）
- 「我该用哪一层」引导
- 8 对象总表
- 「要不要自己搭」决策树

## 法律立场（与 models 站同）

**只索引、只引述、不托管、不解读许可、不给法律意见。**
不复制大段源码，示例代码只取官方文档中的最小片段并标注出处链接。

## 与 models 站的差别

| | models | harness |
|---|---|---|
| 数据来源 | HF API（元数据） | 官方文档 + GitHub 仓库 |
| 更新频率 | 随量化仓发布而变 | 随版本发布而变 |
| 核心风险 | 许可字段缺失 | **「文档说的」与「代码实际做的」可能不一致** |
| 应对 | 标「以发布页原文为准」 | **只写文档明说的，标注文档链接；不推测未写明的行为** |

**这条是 harness 站最容易翻车的地方**：很多框架文档写得漂亮但实现滞后。
所以我们**只写文档明确写了的**，并给出文档链接让读者自己核。
