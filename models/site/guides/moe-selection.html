MoE 选型：总参数、激活参数与真实成本Choosing an MoE model: total parameters, active parameters and real cost从业者视角的方法论 · 关键事实挂官方出处practitioner-perspective methodology · key facts carry official sources

MoE 把「参数量」拆成总参数与激活参数两个数字。选型时要同时算显存、带宽、通信和批量，而不是只看总参数或榜单。An MoE splits “parameter count” into total and active parameters. Selection must budget memory, bandwidth, communication and batch size together, not just total parameters or leaderboard scores.

先分清两个数字Two numbers first

MoE 的「参数量」几乎总要拆成两栏：总参数与每 token 激活参数。
Mixtral 8×7B 每层 8 个专家、每 token 选 2 个，总参数 47B，推理时只激活 13B；
DeepSeek-V3 总参数 671B，每 token 激活 37B。
两个数字回答的是不同问题：总参数决定要装下多少权重，激活参数决定每 token 大约要做多少计算。

省的是算力，不是显存You save compute, not memory

稀疏激活降低的是每 token 的 FLOPs，不是权重占用的显存。
所有专家通常都要常驻显存，或者从内存/闪存按需换入；后者的瓶颈会从算力变成带宽。
粗算显存：总参数 × 每参数字节 + KV cache + 运行时开销。
4-bit 量化的 47B 模型仍需约 24 GB 权重，再叠加 KV cache；13B 激活并不意味着 13B 的显存。
先按总参数选卡，再按激活参数估速度，顺序不能反。

路由与负载均衡Routing and load balance

MoE 的路由器只给每个 token 选少数专家，训练时容易出现「少数专家吃掉大部分 token」的坍塌。
Switch Transformer 用辅助负载均衡损失约束专家利用率；
DeepSeek-V3 报告了无辅助损失的负载均衡策略，并在 14.8T token 预训练中保持稳定。
选型时不要只看「专家数」；要问：推理框架是否支持这套路由、是否有容量因子、超长尾批次会不会把某些专家打爆。

并行与通信Parallelism and communication

专家并行会把不同专家放到不同卡上，token 需要 all-to-all 发送到对应专家再收回。
这会引入通信开销，也会让小批量推理更难摊薄。
单卡能放下时，优先单卡或张量并行；跨机专家并行适合高吞吐服务，不适合低并发交互。
批量越大，路由越容易均衡、吞吐越高；批量小且任务杂时，尾延迟更明显。

选型清单Selection checklist

  • 用总参数 + 量化档位算权重显存，用激活参数估单 token 算力。
  • 确认推理框架支持该模型的路由与专家并行；不支持时，纸面参数没有意义。
  • 测 batch=1 的首字延迟与 batch=32 的吞吐，两者常常差一个数量级。
  • 在你的任务集上比较 MoE 与同激活量的 dense 模型，不要用榜单总分代替。
  • 问清容量因子与丢弃策略：被丢弃的 token 会直接影响答案质量。

边界：以上参数来自各自论文摘要；不同版本的量化、并行配置和上下文长度都会改变实际占用，部署前必须实测。
