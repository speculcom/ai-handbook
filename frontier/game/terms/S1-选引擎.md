# S1 · 选引擎

## 先写四个条件

用一段话写清：2D 还是 3D、发到哪里、最小玩法是什么、你熟悉哪种语言或工具。已有工程和资产也算条件。
不必因为项目只有一个人，就直接排除某个引擎；也不要因为未来可能需要 3D，就现在承担没有必要的工作。

<!-- EN -->
> ## Write four conditions first
>
> State 2D/3D, release platform, minimum gameplay and familiar languages/tools. Existing projects and assets matter too. Team size alone does not exclude an engine; a possible future need for 3D does not automatically justify extra work now.

| 你的要求 | 先查什么 | 可以怎样验证 |
|---|---|---|
| 网页打开即可玩 | 对应版本的 Web 导出、加载与浏览器限制 | 在目标浏览器打开一个最小导出包 |
| 复杂玩法逻辑 | 场景、状态与数据组织方式 | 实现一个循环，检查重启和状态切换 |
| 3D 表现 | 渲染、模型、动画与资源流程 | 放入一个符合目标规模的场景 |
| 已有代码或素材 | 兼容版本、导入与许可 | 导入一个真实资产或模块 |
| 不熟悉工具链 | 官方入门、安装依赖和错误定位 | 按入门文档完成一个小例子 |

<!-- EN -->
> | Requirement | Inspect first | A useful check |
> |---|---|---|
> | Browser play | Versioned Web export, loading and browser limits | Open a minimal export in the target browser |
> | Complex rules | Scene, state and data organization | Implement a loop with restart/state transitions |
> | 3D visuals | Rendering, models, animation and assets | Import a representative scene |
> | Existing work | Version compatibility, imports and licenses | Import one actual asset or module |
> | Unfamiliar toolchain | Official setup/tutorials and error handling | Complete a small official example |

## 先看档案，再做小验证

[Godot](./engine-godot.html)、[Unity](./engine-unity.html)、[Unreal](./engine-unreal.html)、[Bevy](./engine-bevy.html)、[libGDX](./engine-libgdx.html) 的语言、资源流程和导出方式各有不同。按项目要求逐项核对，不用“原生引擎”一个标签判断 Web 支持。

[Phaser](./engine-phaser.html)、[Pixi](./engine-pixi.html) 和 [Three.js](./engine-three-js.html) 的职责也不同。先查场景、渲染、物理、打包分别由谁负责，避免把渲染库当成已经包含全部游戏功能的工具。

<!-- EN -->
> ## Read the profile, then validate a small slice
>
> [Godot](./engine-godot.html), [Unity](./engine-unity.html), [Unreal](./engine-unreal.html), [Bevy](./engine-bevy.html) and [libGDX](./engine-libgdx.html) have different languages, asset pipelines and export options. Check each requirement rather than inferring Web support from the “native engine” label.
>
> [Phaser](./engine-phaser.html), [Pixi](./engine-pixi.html) and [Three.js](./engine-three-js.html) also have different responsibilities. Establish who supplies scenes, rendering, physics and packaging; a rendering library is not automatically a complete game toolchain.

## 一个选型记录示例

以下是假设项目，不是实测推荐：做一个 2D 网页接方块小游戏，已有 JavaScript 经验，希望用键盘和触屏操作。

先比较能覆盖这些约束的候选，检查官方文档对应的版本。用一个场景验证输入、碰撞、计分、重新开始和浏览器导出。记录没通过的条件，再决定保留哪个候选；不用星数或“AI 更擅长哪种语言”代替这个过程。

<!-- EN -->
> ## Example selection record
>
> Hypothetical project, not a measured recommendation: a 2D browser block-catching game, with JavaScript experience and keyboard/touch input.
>
> Compare candidates against those constraints and their versioned docs. Check input, collision, scoring, restart and browser export in one scene. Record failed conditions before selecting; stars or assumed AI language skill are not substitutes.

## 这一步完成后

留下一份选择记录：候选、目标版本、已满足的条件、仍未知的限制和选择原因。接着进入 [核心循环](./s2-核心循环.html)。如果导出平台仍不确定，先看 [Web 导出可行性](./web-导出可行性.html)。

档案中的来源与核验日是公开资料快照，不是本站已经运行过各引擎的证明。

<!-- EN -->
> ## When this step is done
>
> Keep a record of candidates, target version, satisfied conditions, unknown limits and reasons for the choice. Continue to [the core loop](./s2-核心循环.html). If the platform is unresolved, read [Web export feasibility](./web-导出可行性.html).
>
> Profile sources and dates describe public-document snapshots, not execution tests by this site.
