ERC-6551：给每个 NFT 一个链上账户 / ERC-6551: token-bound accounts

交集：ERC-6551 给每个 NFT 派生一个确定性的智能合约账户，NFT 可以自己持有资产、调用应用，不需要改现有 NFT 合约。对 Agent 的意义是“身份即账户”：一个代表 agent/角色的 NFT 可以绑定自己的钱包、权限和资产，持有者转移 NFT 就转移控制权。
适用范围：注册表用 create2 保证地址可预测，账户是实现合约的 ERC-1167 最小代理；执行接口允许有效签名者代账户调用 CALL/DELEGATECALL/CREATE/CREATE2。
未解决：账户安全取决于实现合约与签名者策略，不解决私钥管理、社会恢复或权限撤销；它不是通用 agent 身份标准，跨链和账户抽象组合仍有碎片化。The intersection: ERC-6551 derives a deterministic smart-contract account for every NFT, so the NFT can hold assets and call applications without changing the existing NFT contract. For agents this means identity-as-account: an NFT representing an agent or character can own a wallet, permissions and assets, and transferring the NFT transfers control.
Scope: the registry uses create2 for predictable addresses, accounts are ERC-1167 minimal proxies to an implementation, and the execution interface lets valid signers call CALL/DELEGATECALL/CREATE/CREATE2 on the account’s behalf.
Open: account security depends on the implementation and signer policy; it does not solve key management, social recovery or permission revocation; it is not a general agent-identity standard, and cross-chain/account-abstraction combinations remain fragmented.

OpenID for Verifiable Credential Issuance 1.0

交集：AI agent 或用户需要把「身份、资质、授权」以可验证凭证形式出示给模型/服务；OpenID4VCI 定义签发 API 与密钥证明格式。
适用范围：规范定义凭证签发、proof JWT、nonce 与 issuer 校验；它不规定凭证内容模型（那是 VC data model）也不规定具体信任框架。
未解决：钱包/发行方互操作、撤销与隐私、以及 AI agent 持有凭证时的委托与最小披露，仍需上层 profile 与合规规则。Intersection: AI agents or users need to present identity, qualifications or authorisations as verifiable credentials; OpenID4VCI defines the issuance API and key-proof format.
Scope: the spec defines credential issuance, proof JWTs, nonces and issuer validation; it does not define the credential content model (that is the VC data model) or a specific trust framework.
Open: wallet/issuer interoperability, revocation and privacy, and delegation/minimal disclosure when an AI agent holds credentials still need profiles and compliance rules.

Safe 智能账户：多签、阈值与账户抽象 / Safe smart account: multisig, threshold and account abstraction

交集：把「账户」从一对私钥变成一个合约——Safe 以多签为核心，定义一组 owner 与一个阈值，达到阈值的 owner 确认后交易才执行；owner 可以是 EOA、其他合约账户甚至 passkey。
适用范围：官方文档还列了模块（限额、恢复、4337、passkey）、Guard、批量交易与 Singleton/Proxy 架构；这使「给 Agent 一个有限额度、可回收的账户」在工程上可行。
未解决：模块与 Guard 是安全关键组件，官方明确恶意 Guard 可以阻止交易、锁死资金；阈值多签降低单点风险但不消除私钥管理、社会工程与模块漏洞，机构使用要单独审计。The intersection: turning an account from a key pair into a contract — Safe is multisig at its core, defining a set of owners and a threshold that must confirm a transaction before execution; owners can be EOAs, other smart accounts or even passkeys.
Scope: the docs also cover modules (allowance, recovery, 4337, passkey), guards, batched transactions and the singleton/proxy architecture, which makes “give an agent a capped, revocable account” engineering-feasible.
Open: modules and guards are security-critical, and the docs state a malicious guard can block transactions and lock funds; multisig reduces single-key risk but does not remove key management, social engineering or module bugs, so institutional use needs its own audit.

W3C 去中心化标识符 DID / W3C Decentralized Identifiers (DID)

交集：给智能体、设备或数据集一个可解析的标识，解析出的 DID 文档里放公钥与服务端点，用于证明「我控制这个标识」而无需向某个机构申请。适用范围：规范只定义语法、数据模型、核心属性与解析过程，不规定底层用什么技术或密码学，也不保证文档里的断言为真——作者明确写了 alsoKnownAs 的存在并不证明该断言成立，需要请求方独立核实。未解决：撤销不由验证关系表达，各 DID 方法自行规定；不同方法之间的互操作性不保证；「不需要许可即可证明控制权」不等于「发现与解析不依赖第三方」。The intersection: a resolvable identifier for an agent, device or dataset, whose DID document carries public keys and service endpoints, so control of the identifier can be proven without asking a registry for permission. Scope: the specification defines syntax, data model, core properties and resolution only; it presupposes no particular technology or cryptography, and it does not warrant that assertions in the document are true — the authors state that an alsoKnownAs assertion does not prove itself and requires independent verification by the requesting party. Open: revocation is not expressed through verification relationships and is left to each DID method, interoperability across methods is not guaranteed, and "control provable without permission" does not mean discovery and resolution are independent of third parties.

W3C 可验证凭证 / W3C Verifiable Credentials

交集：把「某机构认证了某个模型、数据集或人员资质」表达成机器可验证的凭证，验证方不必回连签发方。适用范围：规范自己写了两遍——可验证不等于声明为真，验证也不评估声明真实性；采信与否由验证者按自己的业务规则另行判断（规范称 validation，且明说手段差异很大、不在规范范围内）。未解决：撤销与状态检查、信任锚的选择依赖具体实现；凭证里写什么字段、字段含义如何对齐，规范只给数据模型。The intersection: expressing "some body attested this model, dataset or person" as a machine-verifiable credential, so a verifier need not call back to the issuer. Scope: the specification says it twice — verifiability does not imply the truth of the claims, and verification does not evaluate that truth; whether to rely on it is a separate step the verifier performs under its own rules, which the spec calls validation and places outside its scope. Open: revocation and status checking, and the choice of trust anchor, depend on the implementation, and the specification supplies a data model rather than shared field semantics.

Ocean Protocol 数据与算力协议 / Ocean Protocol data and compute protocol

交集：数据访问控制与 compute-to-data——把计算送到数据所在处，让数据不出域也能参与训练或推理，这是「数据可用不可见」在协议层的一种做法。适用范围：官方把三块列为核心组件（数据 NFT 与 datatoken 做门控访问、compute-to-data 做隐私计算、Ocean Nodes 把闲置算力组网），但这是协议定位说明，没有给出可核的合规结论或性能数字。未解决：代币化门控是否满足各地数据保护法规属于法律判断，不是协议能回答的；本站不评价任何部署效果，也不收录代币价格与收益。The intersection: data access control plus compute-to-data — sending computation to where the data sits so data can take part in training or inference without leaving its domain, one protocol-level approach to "usable but not visible". Scope: the vendor lists three core components (data NFTs and datatokens for token-gated access, compute-to-data for privacy-preserving computation, and Ocean Nodes to network idle compute), but this is a positioning statement without verifiable compliance conclusions or performance figures. Open: whether token-gated access satisfies data protection law in a given jurisdiction is a legal judgement, not something the protocol answers; this entry does not rate any deployment and records no token price or yield.

Story Protocol：可编程 IP / Story Protocol: programmable IP

交集：AI 训练数据、模型权重、生成内容都需要可追溯的授权与分成；Story 把 IP 登记、许可与版税写成链上资产 + 链下法律合同。

Scope: the docs define IP Assets (ERC721), Licensing/Royalty/Dispute modules and the Programmable IP License (PIL); on-chain terms are ultimately mapped to real-world law through the PIL.
Open: on-chain registration is not copyright registration; cross-jurisdiction enforcement, multi-source AI training-data licensing and infringement adjudication remain legal problems, not automatic protocol outcomes.

Akash Network：反向竞价的去中心化算力市场 / Akash Network: a reverse-auction marketplace for compute

交集：把 GPU 与容器算力做成公开订单簿——用户用 YAML（SDL）声明 CPU、内存、存储与 GPU 需求，全球独立供应商竞价，用户按价格、位置与信誉选单，按块计费、可随时关闭。
适用范围：官方文档明确它跑 Docker 容器，可用于模型训练、推理服务、Jupyter 与 LLM/扩散模型；支付用与美元挂钩的 ACT 或 AKT。
未解决：「最高省 85%」是官方营销口径，不是本站审计过的价格；供应商的 SLA、数据驻留、网络带宽与故障恢复没有统一保证，生产部署要自行做尽调与压测。The intersection: turning GPU and container compute into a public order book — users declare CPU, memory, storage and GPU needs in YAML (SDL), independent providers worldwide bid, users choose on price, location and reputation, and pay per block with the ability to close at any time.
Scope: the official docs state it runs Docker containers, including model training, inference servers, Jupyter and LLMs/diffusion models; payment uses the USD-pegged ACT credit or AKT.
Open: “up to 85% cheaper” is vendor marketing, not a price this site audited; provider SLA, data residency, network bandwidth and failure recovery are not uniformly guaranteed, so production use needs its own due diligence and load testing.

Bittensor 子网 / Bittensor subnets

交集：把推理与算力当作子网生产的商品，用链上激励结算——这是「去中心化推理」目前最完整的一份官方机制说明。适用范围：官方文档写的是角色分工（矿工生产、验证者打分、子网创建者定义激励、质押者背书验证者），不构成对产出质量或可靠性的保证。未解决：激励如何分配取决于验证者的打分方式，而各子网机制不同，跨子网不可直接比较；本站不评价任何子网的产出效果，也不收录代币价格与收益。The intersection: treating inference and compute as commodities produced by subnets and settled through on-chain incentives — currently the most complete official account of decentralised inference. Open: metadata is not on-chain, so an issuer can change what tokenURI resolves to — on-chain ownership is not content immutability; the standard also does not verify authenticity, copyright or redemption rights, which must be checked separately.
