# 方法论

> 这个文档回答两个问题：**怎么组织数据**，以及**怎么让结论可信**。

---

## 一、为什么需要一套方法论

AI 工具对比面临三个结构性难题：

**① 信息不对称严重**
每个产品的官网都只讲自己。同一功能（比如"后台运行"），有的产品真的能做，有的只是有个入口菜单。**从产品名称推不出能力边界。**

**② 迭代速度远超核验速度**
一个 CLI 两周一版。核验完一周，文档就变了。**任何"最新评测"发布两周后就开始失真。**

**③ 跑分缺乏统一口径**
各家 benchmark 都是自己跑的：自己的题目、自己的参数、自己的判分。**A 的 90 分和 B 的 88 分不可比。**

应对方式不是「更努力地评测」，而是**改变输出的形态**——不做排名，做可核验的档案。

## 二、四条核心规则

### 规则 1 · 放弃总分

**没有统一输入、统一预算、统一环境下的复现实测，就不给总分排名。**

理由不是"测不准"，而是**分数一旦脱离语境就会误导**。用户看到"Claude 94 分"时，得到的信息量约等于零——他不知道这 94 分是在什么任务、什么预算、什么环境下测出来的。

替代方案是**按任务给建议**：

```markdown
## 适合
已有仓库开发、改错、重构、测试与工程交付。

## 注意
只为轻量问答购买最高档；把「最高模型」当成任何任务的默认选择。
```

**判断标准**：这个条目的价值在于「你能据此决定买不买」，而不是「它排在第几」。

---

### 规则 2 · 固定坐标系

**所有对象在同一组 8 个维度下被描述。**

坐标系见 [`axes/`](./axes/)：

| # | 维度 | 核心问题 |
|:--:|---|---|
| 1 | [模型与开放条件](./axes/model-access.md) | 用谁的模型？能不能换第三方？ |
| 2 | [运行位置](./axes/runtime.md) | 本地 / 云端 / 混合？ |
| 3 | [本地文件](./axes/local-files.md) | 能否读写未打开的大文件？ |
| 4 | [关机后的任务](./axes/background.md) | 电脑关了还能跑吗？ |
| 5 | [工具与扩展](./axes/tools.md) | MCP · LSP · 插件 · Hooks？ |
| 6 | [上下文与记忆](./axes/context.md) | 索引算法、上下文窗口、会话恢复？ |
| 7 | [权限与限制](./axes/permissions.md) | 沙箱 · 审批 · 数据出境？ |
| 8 | [适合什么任务](./axes/fit.md) | 这东西最擅长什么？ |

MCP 赛道在这 8 个之外另加 3 个特有维度，见 [`tracks/tools/taxonomy/`](./tracks/tools/taxonomy/)。

**为什么坐标系要固定**：
- **横向可比**：换维度就会毁掉对比能力
- **缺口即信息**：同一个坐标系里，有的对象填满 8 项、有的标 3 个未知，缺口本身就是重要信息
- **可累积**：坐标系不变，历史数据的可比性就被保留下来了

**禁止**：为单个工具自定义维度，或用"特色功能"名目加第九个维度。

### 维度不是等权的

8 个维度**没有默认权重**，但它们在不同赛道的重要性差异极大。
按赛道给出优先级顺序，用它判断「两个对象在关键维度冲突时怎么选」。

#### IDE / CLI 赛道

| 优先级 | 维度 | 为什么 |
|:--:|---|---|
| 1 | [本地文件](./axes/local-files.md) | 不能读写仓库，其他都无从谈起 |
| 2 | [权限与限制](./axes/permissions.md) | 沙箱与审批错了会造成实际损失 |
| 3 | [上下文与记忆](./axes/context.md) | 大仓库表现的决定性因素 |
| 4 | [工具与扩展](./axes/tools.md) | MCP / LSP / Hooks 决定能力上限 |
| 5 | [模型与开放条件](./axes/model-access.md) | 影响成本与可替换性 |
| 6 | [适合什么任务](./axes/fit.md) | 结论层，不是事实 |
| 7 | [运行位置](./axes/runtime.md) | 已知形态后差异有限 |
| 8 | [关机后的任务](./axes/background.md) | IDE/CLI 基本都是"不支持"，区分度低 |

**典型冲突判定**：
- A 的权限控制更严，B 的索引更快 → **先看本地文件的覆盖完整性**，再按「宁严勿松」选 A
- A 支持后台任务，B 的代码索引是本地的 → 看 [运行位置](./axes/runtime.md)，本地索引意味着关机就没了

#### MCP 赛道

优先级完全不同：

| 优先级 | 维度 | 为什么 |
|:--:|---|---|
| 1 | [权限范围](./tracks/tools/taxonomy/scope.md) | **安全第一**，权限失控是直接风险 |
| 2 | [认证机制](./tracks/tools/taxonomy/auth.md) | 认证与授权决定凭据风险 |
| 3 | 权限与限制 | 沙箱与审批 |
| 4 | [传输方式](./tracks/tools/taxonomy/transport.md) | 决定能否被你的客户端用 |
| 5 | 工具与扩展 | 输出是否可消费 |
| 6 | 本地文件 | 赛道特化，看它能碰什么 |
| 7 | 上下文与记忆 | MCP 多为无状态，区分度低 |
| 8 | 运行位置 / 关机后的任务 | stdio 形态下几乎无差异 |

**这条优先级表本身就是本站的差异化内容**：
它明确说「MCP 赛道的第一个问题是安全问题，不是能力问题」。

### 规则 3 · 未知是合法答案

**查不到就写「未知」，并说明为什么查不到。绝不用推测填充。**

标准写法：

```markdown
model_access: >-
  官方价格帮助页区分 Lite / Pro 两档；
  PowerPoint Beta 面向 Pro 与 Max。
  **统一默认模型与全套餐模型映射，本次未核验，记为未知。**
```

不合格的写法：

```markdown
model_access: 应该支持多种模型切换        ← 推测
model_access: 支持全部主流模型             ← 夸大
model_access: 未知                         ← 合格，但不完整
```

**关键**：不完整比错误好。错误会被引用，未知只会促使人去查。

每个赛道条目末尾要写「未知项清单」，把这些没解决的明确列出来：

```markdown
## 未知项清单

以下内容本站未核验，引用时请注意：
- 年付总额
- 关机续跑的完整适用范围
- 跨项目记忆的具体边界
```

### 规则 4 · 每条判断挂证据

**判断能回到官方一手源。**

证据字段格式：

```yaml
sources:
  - label: Cursor · Changelog
    url: https://cursor.com/changelog
    kind: changelog
  - label: Cursor · Pricing
    url: https://cursor.com/pricing
    kind: pricing
```

`kind` 的取值：

| kind | 含义 | 是否必填 |
|---|---|:---:|
| `changelog` | 官方更新日志 / 版本发布页 | **是** |
| `docs` | 官方文档 | **是** |
| `pricing` | 官方定价页 | 强烈建议（D9：label 不写价格数字） |
| `migration` | 迁移 / 退役公告 | 有则填 |
| `engineering` | 厂商工程博客 | 有则填 |
| `repo` | 开源仓库 | 开源项目必填 |

**最低要求**：每个条目至少 2 条来源，且必须包含 `changelog`。

## 三、三种时间语义

这是最容易出错、也最容易被忽略的地方。

| 日期 | 语义 | 用途 |
|---|---|---|
| **发布日期** | 官方宣布的时间 | 说明功能何时出现 |
| **核验日** | 本站读官方文档的时间 | 说明本站信息的时效 |
| **生效日** | 变更实际生效的时间 | 提醒行动截止 |

**三个日期不能混用。**

反例（错误）：
```yaml
last_updated: 2026-10-14   # 这是 GPT-5.5 的生效日，不是本站更新日
```

正例：
```yaml
last_updated: 2026-09-21    # 本站内容更新
last_verified: 2026-09-28   # 本站核验
# 官方 2026-09-14 公告，2026-10-14 生效
```

在 changelog 记录里也要遵守：

```markdown
## 2026-09-28 · 文档核验
Python SDK 已为稳定版；旧 mcp-server 入口已移除，集成迁往 app server。

**适用范围**：适用于当前文档状态，不代表所有客户端已同步。
本站未启用任何本地功能。

**来源**：[OpenAI · Codex SDK](https://developers.openai.com/codex/sdk)
```

**三条纪律**：
1. 发布、灰度、Beta、即将推出、退役——**五个状态词不混用**
2. 补录要声明：`本条于 9 月 19 日核验补录`
3. 核验失败也要记录：`9 月 19 日官方汇总页曾暂未检出；9 月 20 日已恢复`

## 四、价格处理规则（D9 定案：不采不存）

**价格与档位报价不进数据层**（2026-10-20 用户定案，见总纲 D9）。理由：价格高频变动，
本站没有持续定时采集的精力；采了不追等于留死数据，比不采更糟。

- frontmatter 出现 `pricing` / `pricing_pitfalls` → 校验硬失败（反向守卫）。
- 正文不写 `$` 数字、档位报价、价格陷阱条目；「多少钱」一律由 `sources` 里
  `kind: pricing` 的官方定价页链接承担（label 只写档位结构与核验日期）。
- **保留**三类不随价格变动失效的事实：定性口径（免费 / 开源 / 按量 / 随订阅）、
  额度与配额（每日轮数、次数上限、席位规则）、许可。
- 正文叙述里遇到「官方称超量按用量计费」这类**定性计费口径**可以写，数字不写。

## 五、诚实声明利益关系

**有推荐关系就明说，且声明不参与排序。**

如果某工具的链接含邀请码：

```yaml
link:
  url: https://example.com/invite?code=xxx
  kind: invitation        # 官方入口 | 邀请链接
  incentive: 注册得 2000 积分
```

正文必须写：

```markdown
> 保留的邀请链接**不参与编辑排序**，奖励以活动落地页条件为准。
```

**判据**：如果有利益关系却不披露，整个仓库的可信度归零。

## 六、`confidence` 分级

每个条目必须标一个可信度：

| 值 | 条件 |
|---|---|
| `verified` | 8 维度均有官方来源，且核验日在 90 天内 |
| `partial` | 部分维度未知，或核验日超过 90 天 |
| `stale` | 官方已发布重大变化，本站尚未核验 |

**引用数据时必须带 `confidence` 和 `last_verified`。** 这是使用者的责任边界提示。

## 七、实测规范

如果做了实测，必须满足三个条件，否则不准发布结论：

### ① 公开测试设计

```markdown
## 测试环境
- 硬件：<具体配置>
- 系统：<具体版本>
- 网络：<境内直连 / 代理>
- 日期：2026-09-29

## 任务集
T01 仓库上手 · T02 缺陷修复重构 · T03 类型迁移 · T04 性能排查 · T05 构建修复
（每个任务的完整描述见 tasks/）
```

### ② 公开验收标准

```markdown
## 验收标准（每任务）
- 通过：所有断言满足且 tsc 零错误
- 部分通过：主路径可用但有明确缺陷
- 失败：主路径不通或需要人工接管超过 3 次
```

### ③ 承认局限

```markdown
## 本轮局限
- 任务集偏向 TypeScript + Three.js 场景，不覆盖其他技术栈
- 单次运行，未重复验证稳定性
- 部分工具的付费档位未开通，测的是免费额度
```

**失败案例必须记录**。只记成功的实测没有参考价值。

## 八、不做什么

| 不做 | 原因 |
|---|---|
| 不给单一总分排名 | 缺少统一实测 |
| 不推测未核验信息 | 未知比编造有用 |
| 不做跨币种折算 | 折算掩盖区域与账户差异 |
| 不收录无官方文档的对象 | 无法核验 |
| 不把营销话术当事实 | 官网话术不是证据 |
| 不在仓库里放 HTML | 数据层和结论层分离 |
| 不隐藏利益关系 | 有就说 |

## 九、判定标准的优先级

当两条规则冲突时，按这个顺序：

```
安全边界 > 事实准确 > 时间准确 > 完整性 > 简洁
```

举例：

- **安全 vs 完整**：不确定某工具会不会上传代码 → 标「未知」并提醒关注隐私政策，而不是省略这个维度（安全优先）
- **准确 vs 简洁**：抄一段官方描述更省事，但可能省略限定条件 → 自己重写并保留限定（准确优先）
- **完整 vs 简洁**：省略「未知项清单」更简洁 → 写出来（完整优先）

## 十、修改这份方法论

方法论本身可以改，但要：

1. 在 PR 里说明**为什么现有规则不够用**
2. 给出**具体案例**（不是假想场景）
3. 说明**新规则如何避免旧规则的问题**
4. 注明**从哪个版本开始生效**，以及**是否需要回溯修订历史数据**

改方法论比改数据更需要证据。
