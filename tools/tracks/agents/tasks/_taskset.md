# 实测任务集 · IDE / CLI 形态

**基线仓库**：`keel3d`（Three.js + TypeScript + Vite）
**规模**：248 个 TS 文件 / 32,291 行 / 12 个模块（blocks · catalog · engine · game · physics · recipes · net · i18n …）
**验证命令**：`npm run typecheck`（tsc --noEmit）+ `npm test`（460 个断言）
**基线 commit**：`db609d7`

---

## 设计原则

| 原则 | 说明 |
|---|---|
| **基于真实仓库** | 不用玩具代码，32k 行真实项目 |
| **跨文件改动** | 要能验证「改动是否正确」，不是「能否写出一个函数」 |
| **有明确验收** | 每条任务给可执行的判断标准 |
| **不预设答案** | 任务描述不暗示哪种工具更好 |
| **可复现** | 固定 commit，任何人能重跑 |

---

## 为什么选 keel3d

它有四个性质，正好覆盖我们想验证的能力：

| 性质 | 验证什么 |
|---|---|
| 248 个 TS 文件 | 大仓库索引与检索能力 |
| `tsc --noEmit` 可跑 | 类型系统正确性（AI 最容易漏的地方） |
| 460 个断言 | 回归验证能力 |
| 12 个清晰模块 | 跨模块理解能力 |

**关键**：TypeScript 项目里，AI 改完「看起来对」但类型不过的情况非常常见。
这正是 AI 编程工具的真实痛点，也是区分工具的关键点。

## T01 · 仓库上手与验收标准列举

**目标**：让工具先读懂仓库，自己列出可验证的验收标准，然后实现一个最小完整版本。

### 任务描述（原文，可直接喂给任意工具）

```
先阅读 keel3d 的 README 与 package.json，列出这个项目的验证方式
（typecheck / test / build 分别跑什么）。
然后在 src/recipes/ 下新增一个 recipe 条目，注册到 catalog，
使 npm run catalog:check 与 npm test 全部通过。

不要修改任何既有文件，只新增。
```

### 验收标准

| 判定 | 条件 |
|---|---|
| **通过** | `npm run typecheck` 零错误；`npm test` 全绿（460 断言）；diff 只含新增文件 |
| **部分通过** | typecheck 过但 test 有失败，或修改了既有文件但功能正确 |
| **失败** | typecheck 有错误，或 test 失败，或未完成注册 |

### 记录项

- 人工介入次数
- 返工轮次
- 完成时间
- 工具是否主动跑验证命令（**关键观察点**）

## T02 · 缺陷修复（跨文件）

**目标**：修复一个跨多个模块的真实 bug。

### 任务准备（出题人先做）

需要在 keel3d 里植入一个有明确症状的 bug，且症状分散在多个文件。

**建议植入方式**（选一处，不超过 3 个文件）：
- 在 physics 模块改一个常数（如重力系数）
- 让 game 模块的调用方仍用旧假设
- 症状：测试失败但报错信息指向无关文件

> ⚠ **这一条必须先制备并记录植入的 commit**，否则无法判定「工具是否引入回归」。

### 验收标准

| 判定 | 条件 |
|---|---|
| **通过** | 定位到正确的根因文件（不是只改表象）、typecheck 过、test 全绿 |
| **部分通过** | 症状消失但改法影响其他模块，或修好了但引入了新问题 |
| **失败** | 未修复，或修复后仍有测试失败，或改动超出 3 个文件 |

### 关键观察点

- 工具是**定位根因**还是**绕过症状**（改测试让它过 = 失败）
- 是否检查了其他调用点

## T03 · 类型迁移（跨文件，TypeScript 专项）

**目标**：把某个模块的旧写法迁移到新写法，且必须改所有调用点。

### 任务描述（示例形态）

```
把 src/net/ 下的 X API 从 A 形式迁移到 B 形式。
找出所有调用点并全部更新，保证 npm run typecheck 零错误。
```

### 为什么这个任务值得做

**TypeScript 的跨文件迁移是最容易暴露工具水平的地方**：
- 只改了定义处，漏掉调用点 → typecheck 报错
- 一次改太多，出错难定位
- 不确定可空性、加了错误的非空断言 `!`

### 验收标准

| 判定 | 条件 |
|---|---|
| **通过** | 全部调用点更新、typecheck 零错误、test 全绿、无 `as any` 或多余 `!` 逃逸 |
| **部分通过** | typecheck 过但用了类型逃逸（`any` / `!` / `@ts-ignore`） |
| **失败** | 漏掉调用点导致 typecheck 错误，或测试失败 |

**特别检查**：diff 里有没有 `as any`、`!` 非空断言、`@ts-ignore`。
有的话算部分通过 —— 因为这说明是靠压制类型系统过关的。

## T04 · 性能排查（需先有症状）

**目标**：让工具从现象定位到性能瓶颈。

### 任务描述（示例形态）

```
src/engine/ 的 [具体函数] 在 blocks 数量超过 N 时明显变慢。
先给出可复现的测量方法，再定位瓶颈，最后提出优化并验证效果。
```

### 验收标准

| 判定 | 条件 |
|---|---|
| **通过** | 给出**可复现的测量方法**（不是凭感觉）、定位到具体代码行、优化后有**前后对比数据** |
| **部分通过** | 定位准确但没测量数据，或有数据但优化没验证效果 |
| **失败** | 凭猜测改代码，或改了之后无法证明有效 |

### 关键观察点

**这一条最能区分工具等级**：
- 差的：直接改代码，给「感觉更快了」的说法
- 好的：先写测量脚本，给 before/after 数字

**无数据就判失败**，不管结论是否正确。

## T05 · 构建修复（环境相关）

**目标**：解决一个构建层面的真实问题。

### 任务准备

keel3d 的构建是 `tsc --noEmit && vite build`，依赖 Playwright + Chromium。
可以制造一个**依赖或配置层面的问题**（如 package.json 的脚本错误、
tsconfig 的路径配置问题），但不制造纯语法错误。

### 验收标准

| 判定 | 条件 |
|---|---|
| **通过** | `npm run build` 成功，且没有绕过检查（不加 `--force`、不删 typecheck） |
| **部分通过** | build 成功但削弱了检查（如删掉 typecheck 才过） |
| **失败** | build 仍失败，或用了跳过检查的手段 |

**特别检查**：diff 里有没有删掉 `tsc --noEmit` 或加 `--force`。
有就是「削弱检查过关」，判部分通过。

## CLI 形态附加三项

### C01 · 非交互模式可用性

```bash
# 每个 CLI 工具跑一次，检查：
<tool> --print "把 src/config.ts 里的 DEFAULT_TIMEOUT 改成 5000"

# 记录：
- 是否支持单次执行（有 / 无）
- 输出格式（纯文本 / JSON / 混杂日志）
- 退出码语义（成功 0？失败非 0？）
- 能否管道使用
```

| 判定 | 条件 |
|---|---|
| **可用** | 完成任务 + 结构化输出 + 正确退出码 |
| **勉强** | 完成了但输出混杂日志，需二次解析 |
| **不可用** | 无单次模式，或退出码不可靠 |

---

### C02 · 无 TTY 环境

```bash
env -i PATH=/usr/bin:/bin HOME=/tmp/ci <tool> --print "..."
```

| 判定 | 条件 |
|---|---|
| **CI 友好** | 正常运行，无需交互 |
| **需配置** | 加参数/环境变量后可跑 |
| **CI 不友好** | 必须有 TTY，或必然卡在审批 |

---

### C03 · Git 集成深度

| 级别 | 判定 |
|---|---|
| **L0** | 纯文件操作，改完 `git status` 是脏的 |
| **L1** | 能解释 diff，但不能提交 |
| **L2** | 能 `git add` + `commit` |
| **L3** | 能建分支、改完合回 |

**注意**：L0 不算缺陷 —— 有些工具刻意不做 Git 操作。
要区分「设计选择」和「能力缺失」。

## 执行顺序建议

```
T01（上手）→ T02（缺陷）→ T03（类型迁移）→ T05（构建）→ T04（性能）
```

理由：
- T01 是热身，验证工具基本能力
- T02 需要先熟悉仓库（T01 提供）
- T03 是 TypeScript 专项，最能暴露问题
- T04 放最后，因为它需要最深的仓库理解

**每轮之间重置仓库**（`git checkout db609d7` 或 `git stash --all`）。

---

## 每轮必记（缺一项则该轮不予收录）

| # | 项目 | 说明 |
|---|---|---|
| 1 | 环境记录 | CPU / 内存 / 系统 / 网络 / 测试日期 |
| 2 | 仓库 commit | 必须是 `db609d7` 或记录实际用的 |
| 3 | **测试者此前用过的工具** | 避免熟悉度偏差 |
| 4 | 每任务的判定结果 | 通过 / 部分通过 / 失败 |
| 5 | 人工介入次数 | 中途帮它解决问题的次数 |
| 6 | 返工轮次 | 它做完后你发现不对、要求重来的轮次 |
| 7 | 完成时间 | 自然时间，不含你等待的时间 |
| 8 | **失败案例原文** | 引用它的输出/报错，不要概括 |
| 9 | 局限说明 | 本轮不能代表什么 |

---

## 判定纪律

| 规则 | 说明 |
|---|---|
| **改测试让它过 = 失败** | 不管功能多完整 |
| **删掉检查项过关 = 最多部分通过** | 如删 `tsc --noEmit`、加 `--force` |
| **类型逃逸 = 最多部分通过** | `as any` / `!` / `@ts-ignore` |
| **凭猜测无数据 = 失败** | 尤其 T04 性能任务 |
| **必须记录失败案例** | 只记成功的实测不收录 |
