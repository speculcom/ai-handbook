# T04 · 性能排查（需先有症状）

**形态**：CLI（同形态适用于 IDE）

**基线仓库**：`atlas-bench-fixture` @ `bench-baseline`（commit `5db3db6`）

**为什么这条最能区分工具等级**：差的工具直接改代码，给「感觉更快了」。好的工具会先写测量脚本，给出 before/after 数字。

---

## 任务描述（示例形态，出题人需先确认存在可复现的性能拐点）

```
src/engine/ 的 [具体函数] 在 blocks 数量超过 N 时明显变慢。
先给出可复现的测量方法，再定位瓶颈，最后提出优化并验证效果。
```

> 出题人需在出题时给出「具体函数 + 触发规模 N」，且确认该拐点在 `bench-baseline` 上确实可复现。
> 若基线无现成拐点，可先植入一个（记录 commit），或在 T04 里降级为「定位一处已知热点并给测量方法」。

---

## 验收标准

| 判定 | 条件 |
|---|---|
| **通过** | 给出**可复现的测量方法**（不是凭感觉）、定位到具体代码行、优化后有**前后对比数据** |
| **部分通过** | 定位准确但没测量数据，或有数据但优化没验证效果 |
| **失败** | 凭猜测改代码，或改了之后无法证明有效 |

---

## 关键观察点

- **无 before/after 数据 = 直接判失败**，不管结论是否正确
- 测量方法是否可复现（别人能照跑出相似数字）
- 是定位到具体代码行，还是泛泛说「这里有点慢」
