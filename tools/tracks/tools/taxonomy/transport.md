# MCP 特有维度 A · 传输方式

> 核心问题：**客户端怎么连上这个 server？**

---

## 为什么这个维度决定运行位置

MCP server 的传输方式**直接决定它在哪运行、能不能持续存在**。

| 传输 | 运行形态 | 电脑关了会怎样 |
|---|---|---|
| stdio | 本地子进程 | 随客户端一起死 |
| SSE / HTTP | 远程服务或本地服务 | 远程的继续；本地服务看怎么起的 |

---

## 三种传输

### stdio

```
本地进程，通过标准输入输出通信。
由客户端作为子进程启动。
```

| 属性 | 说明 |
|---|---|
| 运行位置 | 本地 |
| 认证 | 无协议层认证（靠进程权限） |
| 生命周期 | 绑定客户端进程 |
| 典型场景 | 本地文件操作、本地 git |

**关键**：stdio server 的"权限边界"就是**运行它的那个用户的文件权限**。没有额外认证层。

### SSE（Server-Sent Events）

```
HTTP 长连接，客户端通过 SSE 接收消息，
通过单独的 POST 端点发送。
```

| 属性 | 说明 |
|---|---|
| 运行位置 | 远程服务或本地独立服务 |
| 认证 | HTTP 层（OAuth / Token / 无） |
| 生命周期 | 服务端独立 |
| 典型场景 | 远程数据库查询、多人共享服务 |

### Streamable HTTP

```
HTTP POST 发送消息，可选 SSE 流式返回。
MCP 规范的新传输方式。
```

| 属性 | 说明 |
|---|---|
| 运行位置 | 远程或本地 |
| 认证 | HTTP 层 |
| 生命周期 | 服务端独立 |
| 状态 | 较新，部分 client 支持待确认 |

---

## 判定要点

### ① 支持哪些传输

```
支持 stdio 与 Streamable HTTP；
SSE 支持情况本次未核验，记为未知。
```

**必须逐项列**，不能写"支持远程"。

### ② 多传输共存

有些 server 同时支持 stdio 和 HTTP，**但两边权限可能不同**。

```
stdio 模式继承客户端用户权限；
HTTP 模式需另行配置认证。
```

这种情况必须写清，因为**权限边界完全不同**。

### ③ 是否只支持旧版

规范在演进。只支持旧传输的 server，在新客户端上可能不可用。

```
仅支持 stdio；未声明对 Streamable HTTP 的支持。
```

### ④ 本地独立服务的例外

有些工具虽然用 HTTP，但可以在本地起一个常驻服务。

**这种情况要写清**：
```
可在本地启动 HTTP 服务；
此时电脑关闭后服务停止，与 stdio 无本质差异。
```

---

## 常见错误

| 错误写法 | 问题 |
|---|---|
| `支持远程` | 没说哪种传输 |
| `本地运行` | 没说用 stdio 还是本地 HTTP |
| 省略 | 无法判断部署形态 |

---

## 合格写法

```yaml
mcp:
  transport: >-
    支持 stdio 与 Streamable HTTP。
    stdio 模式继承客户端用户权限；
    HTTP 模式需配置 Token。
    生命周期随客户端进程，客户端退出即停止。
```

拆解：
- 传输列全了
- 两种模式的权限差异说清了
- 生命周期说清了

---

## 与客户端的兼容性

**这是实操中最容易踩的坑**。

| 情况 | 症状 |
|---|---|
| server 只支持 stdio，但你在用远程客户端 | 连不上 |
| server 只支持旧版 SSE，客户端已迁到 Streamable HTTP | 连不上 |
| server 声明支持但实际有 bug | 连上但不稳 |

**建议实测时记录**：这个 server 在哪些客户端里验证过可用。
