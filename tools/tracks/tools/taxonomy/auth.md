# MCP 特有维度 B · 认证机制

> 核心问题：**谁来用这个 server？怎么证明身份？**

---

## 为什么认证是独立维度

因为 MCP 的认证**不是 MCP 协议强制的**，而是各 server 自己实现的。

这导致一个反直觉的事实：

> **本地 stdio server 通常"没有认证"，但不代表它没有权限边界。**

它的边界就是运行它的那个用户的文件权限。

---

## 四档认证

| 档位 | 机制 | 风险 |
|---|---|---|
| **无认证** | 任何能连上的人都能用 | 取决于传输方式 |
| **静态凭据** | API Key / Token 写在配置里 | 凭据泄露风险 |
| **用户授权** | OAuth / 用户名密码 | 需处理 token 刷新 |
| **能力审批** | 每个敏感动作需人工批准 | 最低风险，但打断流程 |

---

## 关键区分：认证 ≠ 授权

| 概念 | 回答什么 |
|---|---|
| **认证**（auth） | 你是谁？ |
| **授权**（scope） | 你能做什么？ |

很多 server 有认证但没授权（知道你是谁，但允许你做所有事），
或者有授权但没认证（只能访问特定目录，但任何人都能访问）。

**两个都要查，都要写。**

---

## 按传输方式的常见组合

| 传输 | 常见认证 | 说明 |
|---|---|---|
| stdio | 无协议层认证 | 靠进程权限 |
| HTTP 本地 | Token / 无 | 需自己实现 |
| HTTP 远程 | OAuth / API Key | 可能有完整流程 |

**stdio 的特殊性**：

```
stdio 模式继承启动它的客户端用户的全部文件权限，
无独立认证层。
```

这不是缺陷，是形态决定的。**但使用者必须知道**——
如果客户端进程本身权限很高，这个 server 的权限也很高。

---

## 凭据管理

**这是最实用的信息**，因为凭据泄露是真实风险。

要查清：

| 问题 | 意义 |
|---|---|
| 凭据存哪 | 配置文件 / 环境变量 / 系统 keychain |
| 会不会进日志 | 调试日志是否脱敏 |
| 支持哪些凭据 | 完整 PAT 还是只读 PAT |
| 能不能收紧 | 最小权限原则能否实践 |

**特别关注脱敏**：

```
调试凭据脱敏
```

有些工具的调试日志会把 token 打出来。这是必须记的。

---

## 组合风险

**多个 server 叠加时，凭据会分散**。

| 情况 | 风险 |
|---|---|
| 3 个 server 各用一个只读 token | 可控 |
| 3 个 server 各用一个完整 token | 泄露面 ×3 |
| 1 个 server 持有全部 token | 单点风险 |

**能写清"建议用只读 token"是有价值的信息。**

---

## 判定要点

### ① 有无独立认证

```
HTTP 模式需配置 API Key；stdio 模式无独立认证层。
```

### ② 凭据类型与最小权限

```
支持只读与完整 PAT；
建议按需使用只读权限。
```

### ③ 凭据存储与日志

```
凭据从环境变量读取；
文档提示避免硬编码在配置文件中。
**调试日志是否脱敏本次未核验，记为未知。**
```

### ④ 审批能力

```
无独立审批机制；
所有动作需调用方自行控制。
```

**对比有审批的**：
```
独立审批组件检查外部动作；敏感操作需批准。
```

后者信任级别明显更高。

---

## 常见错误

| 错误写法 | 问题 |
|---|---|
| `无需认证，安全性好` | 事实错误 + 结论错误 |
| `使用 Token` | 没说存哪、能不能收紧 |
| 省略 | 无法判断风险等级 |

---

## 合格写法

```yaml
mcp:
  auth: >-
    HTTP 模式需配置 GitHub Token（支持只读与完整权限）；
    stdio 模式无独立认证层，继承客户端用户权限。
    凭据从环境变量读取。
    **调试日志是否脱敏本次未核验，记为未知。**
```

拆解：
- 两种模式的认证分开说
- 凭据权限可选性写清了
- 凭据来源写清了
- 不知道的标出来

---

## 安全提示

**本维度的记录不构成安全评估。**

它只记录**官方声称的机制**和**文档所述的配置方式**。
真实安全性取决于：
- 你怎么配置凭据
- 客户端进程本身的权限
- 机器上还有什么能访问这些资源的东西
